# 100,000 virtual vehicles on AWS EC2: measured runs (1 October 2026)

The prototype uses software-generated telemetry to simulate a fleet of autonomous vehicles. **No physical vehicles or sensors are involved.** Every number below was read by hand from the running components (simulator `/metrics` and `/status`, Node-RED `/stats`, telemetry-service and alert-service `/stats`, `docker stats`, `top`/`vmstat`) during the run. None are estimated.

## Environment
- **Instance:** AWS Academy Learner Lab, us-east-1, one EC2 **t3.large** (2 vCPU, 8 GiB), Amazon Linux 2023
- **Stack:** the full stack under Docker Compose on that single instance: Mosquitto, Node-RED, Kafka (KRaft), Redis, MongoDB (local container), telemetry/alert/analytics services, backend, Prometheus, Grafana, exporters, and the simulator itself
- **Simulator:** `MODE=load_test`, `VEHICLE_COUNT=100000`, `VEHICLES_PER_CONNECTION=2000` (50 MQTT gateway sessions), `EMERGENCY_EVENT_RATE=0.00002`
- **Restarts:** each run started from empty volumes (`docker compose down -v`)

## Bug found and fixed during the first run
Run 0 (60 s interval, before the fix) produced **34,909 `ROUTE_DEVIATION` events** in about 2 minutes, flooding the alert path.
- **Cause:** each vehicle was integrated in a straight line for the whole 60 s step (about 800 m). It overshot route corners by more than the 150 m deviation threshold.
- **Fix:** `simulator/fleetsim/vehicle.py`. Steps longer than `LARGE_STEP_S` (5 s) now move the vehicle the same distance *along* the route waypoints, so a long reporting interval no longer changes where the vehicle is.
- **Offline check:** 2,000 vehicles × 20 steps of 60 s produced 10,555 deviations before the fix and 0 after.
- **Cost:** about 27 µs per vehicle step, unchanged.
- **Regression test:** `test_large_time_step_does_not_create_false_route_deviation`.

After the fix, a 60 s run produced **2** route deviations in about 4 minutes (both genuine, from the random-scenario injector).

## Run 1: 100,000 vehicles, 60 s interval (target ≈ 1,667 telemetry msg/s). Overloaded
Snapshot at uptime 249 s:

| Metric | Value |
|---|---|
| Simulator schedule lag | 48.7 s (cannot keep its own schedule) |
| Telemetry published by simulator | 301,243 (≈ 1,210/s, below the 1,667/s target) |
| Node-RED received / sent to Kafka | 185,424 / 169,337 |
| Node-RED edge latency p50 / p95 | 12.6 s / 19.7 s |
| Telemetry service inserted | 151,980; vehicles seen 84,087 |
| End-to-end latency p50 / p95 | 66.2 s / 88.1 s |
| CPU (all containers combined) | ≈ 185 % of 200 % |

**Verdict:** a single 2 vCPU instance cannot run the full stack plus 100,000 vehicles at 60 s.

## Run 2: 100,000 vehicles, 120 s interval (target ≈ 833 msg/s). Not stable
| Metric | at 238 s | at 395 s |
|---|---|---|
| Schedule lag | 0 s | 0 s |
| Published telemetry | 191,587 | 307,120 (between snapshots: ≈ 831/s, on target) |
| Node-RED received | 197,880 | 303,418 (keeps up) |
| Node-RED → Kafka sent | 166,431 | 254,431 (≈ 590/s, falling behind) |
| Inserted into MongoDB | 166,385 | 252,372 |
| Distinct vehicles seen | **100,000** | **100,000** |
| End-to-end p50 / p95 | 32.9 s / 40.7 s | 72.1 s / 92.4 s (growing) |
| CPU | `vmstat`: 82–89 % user, 11–18 % system, **0 % idle, 0 % steal** | |

**Verdict:** the simulator and MQTT ingestion keep up at 833 msg/s. The Node-RED → Kafka → telemetry-service chain sustains only about 590 msg/s while sharing 2 vCPU with everything else, so the backlog grows. The limit is CPU saturation, not AWS throttling (0 % steal).

## Run 3: 100,000 vehicles, 300 s interval (target ≈ 333 msg/s). **Stable**
| Metric | 16:36:09 UTC | 16:39:21 UTC |
|---|---|---|
| Published telemetry | 94,000 | 158,000 (64,000 in 192 s = **333 msg/s**, exactly on target) |
| Node-RED received | 94,000 | 158,000 (0 lost) |
| Node-RED → Kafka sent | 94,017 | 158,030 (includes events) |
| Inserted into MongoDB | 93,999 | 157,992 (8 in flight) |
| Distinct vehicles seen | 93,999 (first 300 s cycle not yet complete) | **99,998** |
| Simulator schedule lag | – | **0 s** |
| False `ROUTE_DEVIATION` events | 0 | 0 |
| End-to-end latency p50 / p95 / p99 | 1.62 s / 3.20 s / 3.62 s | **1.62 s / 3.41 s / 4.69 s** |
| Alerts created / alert latency p50 / p95 | 17 / 1.33 s / 2.63 s | 30 / 1.64 s / 2.63 s |
| CPU (`vmstat`) | – | 70 % user, 8 % system, **18 % idle**, 4 % steal |

**Verdict:** a single t3.large running the whole stack sustains **100,000 virtual vehicles reporting every 300 s (≈ 333 telemetry msg/s)** with no loss, a flat end-to-end p95 of about 3.4 s, and CPU headroom left.

## How to describe this accurately
- ✅ "100,000 software-simulated vehicles, each reporting every 5 minutes (≈ 333 msg/s), ran on one EC2 t3.large with no message loss and an end-to-end p95 of 3.4 s."
- ✅ "At 60 s and 120 s intervals (1,667 and 833 msg/s), the single 2 vCPU instance saturated (0 % idle). The measured ceiling of the Node-RED → Kafka → MongoDB chain on this box is about 590 msg/s."
- ❌ Do not say "100,000 vehicles at 1 message per second" or "100,000 msg/s". That is about 300 times more than what was measured.
- ❌ Do not say physical vehicles were tested.
- **Scaling beyond this:** the design scales out by adding Node-RED replicas (MQTT shared subscription, measured 50/50 split in the sandbox), Kafka partitions, and telemetry-service consumers (KEDA). See `docs/ARCHITECTURE.md` §7. That part is **design, not measured**.

## Reproduce
```bash
# in ~/av-fleet-sim/.env
MODE=load_test
VEHICLE_COUNT=100000
TELEMETRY_INTERVAL=300
VEHICLES_PER_CONNECTION=2000
EMERGENCY_EVENT_RATE=0.00002

docker compose down -v && docker compose up -d
# wait at least 2 reporting intervals (10 min), then sample twice, a few minutes apart:
python3 ~/m.py      # the counters/latency script used for the table above (scripts/measure_snapshot.py)
vmstat 2 2
```
