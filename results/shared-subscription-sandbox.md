# Horizontal scaling check: two Node-RED replicas behind an MQTT shared subscription

Measured in the cloud sandbox (2 vCPU / 7.8 GB). Edge tier only (Node-RED with `KAFKA_ENABLED=false`).
Two Node-RED instances (ports 1880 and 1881) ran the same `flows.json`, subscribed to
`$share/nodered/fleet/+/telemetry`. The simulator ran 1,000 virtual vehicles at 1 msg/s for 30 s.

| | Telemetry | Events | Edge p50 | p95 | p99 |
|---|---|---|---|---|---|
| Generated by simulator | 30,000 | 24 | | | |
| Node-RED #1 received | 15,000 | 12 | 3 ms | 6 ms | 7 ms |
| Node-RED #2 received | 15,000 | 12 | 4 ms | 6 ms | 8 ms |
| **Total received** | **30,000** | **24** | | | |

Result: Mosquitto split the stream exactly 50/50 with nothing lost and nothing duplicated. Adding a
replica needs no configuration change, which is how the ingestion tier scales out.

Caveat found by this test: Mosquitto hands out shared-subscription messages round-robin *per message*,
not per vehicle. So each replica sees only part of every vehicle's sequence, and its per-vehicle gap
counter no longer means anything (measured: about 12,700 "sequence gaps" per replica even though nothing was lost). It also means a duplicate can land on the
other replica, where edge de-duplication misses it. The unique `message_id` index in MongoDB is the
backstop. In production, use a broker with a sticky shared-subscription strategy (for example EMQX
`hash_clientid` or `hash_topic`) so each vehicle always maps to the same replica.
