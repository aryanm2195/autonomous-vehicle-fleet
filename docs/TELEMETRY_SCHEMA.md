# Telemetry and event schema

All payloads are **generated by the software simulator**; `simulation.simulated` is always `true`.
Machine-readable definitions: [`schemas/telemetry.schema.json`](../schemas/telemetry.schema.json) and [`schemas/event.schema.json`](../schemas/event.schema.json) (JSON Schema 2020-12). The unit test `test_generated_messages_validate_against_json_schema` checks generated messages against both.

## MQTT topics
| Topic | QoS | Payload |
|---|---|---|
| `fleet/{vehicle_id}/telemetry` | 0 | telemetry (below), one per vehicle per `TELEMETRY_INTERVAL` |
| `fleet/{vehicle_id}/events` | 1 | event (below), on detection |
| `fleet/{vehicle_id}/status` | 1, retained | `{"state":"online"}`, or `offline` via Last Will (per-vehicle mode) |

## Telemetry example (as generated)
```json
{
  "schema_version": "1.1.0",
  "message_id": "6d631825-7bb3-4150-a7c7-1d37915e2069",
  "vehicle_id": "vehicle-00020",
  "sequence": 200,
  "timestamp": "2026-09-27T09:28:15.042Z",
  "location": { "latitude": -37.838674, "longitude": 144.937369, "altitude_m": 31.4,
                "speed_kmh": 58.1, "heading": 90.6, "accuracy_m": 2.5, "gps_status": "OK", "fix": "GNSS" },
  "battery":  { "percentage": 85.29, "charging": false, "estimated_range_km": 387.7 },
  "lidar":    { "status": "OK", "obstacle_detected": false, "distance_m": 74.78, "object_count": 1 },
  "radar":    { "status": "OK", "object_detected": false, "distance_m": null, "relative_speed_mps": 0.0 },
  "camera":   { "status": "OK", "object_detected": false, "object_type": null, "confidence": 0.0 },
  "safety":   { "time_to_collision_s": null, "emergency_braking": false, "deceleration_mps2": 0.0 },
  "vehicle":  { "status": "IN_SERVICE", "activity": "TRIP", "passenger_count": 3, "trip_id": "trip-85a1837ea0",
                "route_id": "route-3607c037", "route_deviation_m": 9.7, "odometer_km": 57764.17 },
  "traffic":  { "status": "LOW", "congestion_index": 0.15 },
  "simulation": { "simulated": true, "mode": "demo" }

```
After Node-RED, an `ingest` block is added (`received_at`, `edge_latency_ms`, `gateway`, `mqtt_topic`, `priority`) together with `location.speed_mps`. MongoDB documents also get `ts` (BSON date) and `geo` (a GeoJSON Point).

## Improvements over the example schema in the brief
| Addition | Why |
|---|---|
| `schema_version` | Lets consumers handle schema changes over time |
| `message_id` (UUID) | End-to-end de-duplication (Node-RED) and idempotent MongoDB writes (unique index) |
| `sequence` | Per-vehicle gap and reordering detection (counted in Node-RED stats) |
| ms-precision UTC `timestamp` | End-to-end latency measurement at every stage |
| `altitude_m`, `accuracy_m`, `gps_status`, `fix` | GPS quality. A failed GNSS switches to `DEAD_RECKONING` instead of sending null coordinates |
| `status` on every sensor (`OK/DEGRADED/FAILED`) with null readings on failure | Sensor-failure scenarios are explicit and machine-checkable |
| `radar.relative_speed_mps` (renamed from `relative_speed`, unit in name) | No unit ambiguity. Negative means closing |
| `safety.time_to_collision_s`, `emergency_braking`, `deceleration_mps2` | Lets the platform re-derive collision and sudden-braking alerts independently of vehicle events |
| `battery.estimated_range_km` | Used for charging decisions |
| `vehicle.activity`, `trip_id`, `route_id`, `route_deviation_m`, `odometer_km` | Finer detail than the 6 statuses, trip tracking, route-deviation detection and maintenance scheduling |
| `traffic.congestion_index` | Numeric form of the traffic level for analytics |
| `simulation.simulated`, `simulation.mode` | Makes it explicit in the data that it is synthetic |

Conditional rules in the schema: `IN_SERVICE` ⇒ `passenger_count ≥ 1`; `AVAILABLE/IDLE/CHARGING/MAINTENANCE` ⇒ `passenger_count = 0`.

## Event example
```json
{
  "schema_version": "1.1.0",
  "message_id": "…uuid…",
  "event_id": "evt-3f9c2a7b1d20",
  "vehicle_id": "vehicle-00007",
  "timestamp": "2026-09-27T09:39:17.722Z",
  "event_type": "COLLISION_WARNING",
  "severity": "CRITICAL",
  "source": "VEHICLE",
  "location": { "latitude": -37.8121, "longitude": 144.9587 },
  "vehicle_status": "IN_SERVICE",
  "details": { "object_type": "pedestrian", "distance_m": 11.2, "time_to_collision_s": 1.01,
               "speed_kmh": 40.0, "required_decel_mps2": 6.4 },
  "simulation": { "simulated": true, "mode": "demo" }
}
```

| `event_type` | Severity | Raised when (on board) | Platform rule (alert-service) |
|---|---|---|---|
| `COLLISION_WARNING` | CRITICAL | required deceleration > 5.5 m/s² and TTC < 3 s (AEB engages) | TTC < 2 s and `emergency_braking` |
| `SUDDEN_BRAKING` | HIGH | deceleration > 6 m/s² | – |
| `OBSTACLE_DETECTED` | MEDIUM | obstacle or road barrier < 20 m ahead while moving | – |
| `LOW_BATTERY` | MEDIUM | battery crosses `LOW_BATTERY_THRESHOLD` (with hysteresis) | battery < low and not charging |
| `CRITICAL_BATTERY` | CRITICAL | battery crosses `CRITICAL_BATTERY_THRESHOLD` | battery < critical and not charging |
| `SENSOR_FAILURE` | HIGH | a sensor changes to FAILED | any sensor `status == FAILED` |
| `ABNORMAL_SPEED` | HIGH | speed > 100 km/h | speed > 100 km/h |
| `ROUTE_DEVIATION` | HIGH | > 150 m from the planned route | `route_deviation_m` > 150 |
| `EMERGENCY_STOP` | CRITICAL | operator or scenario initiated | – |
